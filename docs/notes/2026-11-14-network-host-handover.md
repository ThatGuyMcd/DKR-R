# Networking and host handover work

This work is on `codex/network-host-handover`, above the issue 45 packaging repair. It has not been published or deployed.

The implementation adds authenticated direct input paths between racing members. The current host still relays and repairs inputs, and remains the authority for membership, scene transitions and confirmation. Eight spectators remain outside the four-racer input mesh. Introduced peer keys grant input delivery privileges only; the receiver still checks the current controller lease and input owner.

Planned host handover runs in the waiting lobby, including after returning from a race. It does not provide crash failover or move authority during a live simulation. The candidate must accept. All connected members must prepare the same session snapshot and prove their successor routes before commit. Controller ports remain unchanged. Lost commit acknowledgements hold race start; they never restore the former host after commit. The former host coordinates release and retransmission until everyone has installed the new authority.

The original persistent save owner stays separate from the networking host. A successor receives the shared online EEPROM, controller Paks and custom records in memory and retains a match-scoped online session bank. It must not replace its personal Adventure or unrelated online save. Pair-key inventory is sent privately to the successor; other members receive only its digest.

The candidate checks its own local consent, even when acceptance is relayed by the former host. Departed-member pair keys are wiped before constructing another transfer inventory, and clients release their retired introduced routes. Pair encryption counters survive role changes. Private direct-connect invitations are not copied into the directory-code field.

Connection probes use the realtime input lane. After installing the new role, the successor clears old heartbeat measurements and proves fresh round trips to every racer before acknowledging activation. The old coordinator publishes completion only after that proof. This retains the existing race-start connection check and avoids announcing readiness before an immediate Start request can pass it.

Optional racer-route recovery is separate from the authority connection. An introduced racer cannot replace the host bootstrap or invitation code, and a failing optional route cannot trigger the client's host reconnect. Host changes also need the manual clock reference and shared menu input policy to follow the successor's existing controller port. Ordinary racing input keeps the original controller assignments. A spectator host leaves the game's shared menu controller on the first racing port.

Public lobby handover also requires an atomic ownership operation on the existing directory. Its account and instance checks must agree with the already admitted native successor. The existing room ID and membership survive the transfer. The directory feature is capability gated, so an older deployed service cannot silently produce a partially transferred public lobby. No new player software or third-party service is required. The matching existing backend update still needs deployment review after preparation and testing.

## Validation

- Local exported API, service binding and SQLite Durable Object: 205 checks passed, including four racing slots and eight spectator slots, matching candidate consent, another instance of the same account, altered state digests, repeated commit acknowledgement, sequential handovers, a spectator accepting hosting and the former host leaving.
- The ROM-free host build completed. The full Linux CTest run passed 173 of 174 tests; its regression harness timed out. The same regression harness passed on Windows with native CMake and Git (25 tests, one skipped). Four targeted networking CTests passed after restoring the frozen interfaces.
- Native Windows and Linux tests passed sequential transfers to a racer and then a spectator, with four racing slots and eight spectators, unchanged controller leases and unchanged save ownership. The delayed variant passed with 375 ms delivery delay in each direction, jitter, 200 ms spikes, periodic realtime packet loss and a 128 KiB Pak preserved at every member. These tests use actual DirectSession sockets and encryption with synthetic save data. They do not run a guest ROM. The successor must pass the existing start connection check immediately when completion is reported. The tests then run the actual synchronized countdown after injecting a stale pre-roster start receipt.
- The pattern guard and checksum-pinned-file checks passed. The full Windows guard/tooling suite passed after selecting native CMake and Git. The installed pre-commit checks passed.
- Windows and Linux game builds passed. The disposable-profile qualification hook waits for all twelve members, transfers to the racer on controller port one and starts the normal game afterward. Early actual Quick Join runs exposed missing route aliases, stale start receipts and an immediate Start request racing the new host's heartbeat proof. Each now has a regression test. Normal UI sessions still require the candidate's consent.

These are local test results, not physical Steam Deck or intercontinental gameplay measurements. Actual nonempty-mod handover followed by another mod download still needs a guest-game check; native transfer tests cover verified cache promotion separately.

### Actual game qualification

- R17, paced Quick Join admission: twelve real game processes, four racers and eight spectators, transferred hosting to the second racing port and entered a normal race. All twelve exited successfully. All four racers recorded zero race input-wait time.
- R17, paced admission with 375 ms common receive delay in each direction, 25 ms jitter, 200 ms spikes and periodic realtime/replica loss: all twelve completed. A slow spectator also received 1,000 ms delay and 1,000 ms spikes. Racer input waits were limited to the first roughly 75 race frames; their total measured waits were 35.739, 96.532, 0 and 497.598 ms. These are application-delivery impairments on every route, not measured WAN RTT or a wire shaper.
- R20, simultaneous admission after separating authority recovery: all twelve real Quick Join game processes completed host transfer and racing. All four racers recorded zero race input waits. Its old spectator counter included menu simulation, so it is not used as proof of sustained race playback.
- R21/R23 failed before commit and preserved the original host. Tracing found that an authorized Quick Join reservation could exist without a peer object; renaming that route for the successor then failed. R24 repairs the reservation alias and its release bookkeeping. Native coverage checks alias collisions and repeated reservation release.
- R24 then exposed a descriptor accepted before the new roster arrived. Repeating the descriptor did not refresh the client's cached roster receipt. R26 revalidates the receipt when roster or shared-save identity changes; its native test completes the real countdown after injecting that order of events.
- R27 removes unsent obsolete observer checkpoint chunks and confirmed-frame batches when replacing a spectator transfer. It preserves current-transfer data, other recipients, other games, exact input repair and live controls. Spectators also retain an already approved checkpoint decode when receiving the matching release, instead of requesting the same baseline again.
- R27 Windows burst-admission stress: all twelve processes exited zero after handover and a normal race. Each racer had 375 ms common receive delay, 25 ms jitter, 200 ms spike windows and periodic realtime/replica loss. One spectator had 1,000 ms delay and 1,000 ms spikes. Racing input-wait totals were 0 / 101.286 / 0 / 0 ms; the only nonzero sample was the first race interval, around frame 84. Every later reported interval was zero for all four racers. This is not an absolute zero-wait claim.
- The R27 spectator acceptance check requires at least 300 additional simulated frames between two samples from the actual race epoch. All eight passed the Windows stress run; their observed race deltas ranged from 623 to 800 frames. Earlier runs checked a cumulative menu-plus-race counter and are excluded from this stronger result.
- R27 mixed-platform functional run: a Linux AppImage succeeded the original Windows host, all twelve completed handover, all four entered a race, and all eight spectators advanced by 1,303-1,627 additional race frames. The first report parser rejected an interleaved log token; the saved logs were recovered with numeric-field parsing. All workers recorded clean retirement. The repeat passed with all twelve exit codes zero, no reported rollback failures, and spectator race deltas of 1,298-1,629 frames. Exit codes are saved before parsing the runtime logs.
- The latest full ROM-free Linux host run again passed 173/174 checks, with two child commands timing out in the regression harness under WSL/NTFS. The unchanged regression harness passed its 25 cases (one skipped) on native Windows. Windows guard/tooling and installed pre-commit checks passed. The host-port menu routing policy tests passed for all four possible host ports, shared menus, ordinary racing, unassigned ports and nested construction contexts.

The mixed-platform run is functional evidence only. WSL's monotonic clock ran about nine percent away from its raw clock and native Windows time. This Codex process had no Administrator token, so the previously authorized VM time-service lease could not be used. No time service was changed or paused. Linux rendering in this fixture uses Xvfb/lavapipe, not Steam Deck hardware. Its timing and frame-rate totals are excluded.
