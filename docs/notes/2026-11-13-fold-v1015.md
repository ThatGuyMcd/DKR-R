# Fold catch-up to v1.0.15, 2026-11-13

The fold branch stood at the v1.0.12 comparison (main `d457741`). Main then
shipped v1.0.14 and v1.0.15 through the layer chain: 87 layer files changed,
195 source files and 13 CMake modules were added, and 23 base sources changed.
This note records how `refactor/fold-current-main` was brought to main
`4e461ea` (tag `Version1.0.15` is `d292530`; the ten later commits change no
layer). Nothing here was pushed, deployed or released.

## Method

1. Merged `origin/main`. The 58 layer files main had edited stay deleted.
2. Configured main `4e461ea` with the full release chain in the
   `dkr-ci-linux-full` image (`sha256:4d389ad0...`) and scanned what its 1,378
   shipped translation units read. Same private inputs and the same two camera
   manifest exceptions as the `d457741` reference. `BUILD_TESTING=OFF`: with
   tests on, the capsule's camera overlay rejects the storage module that
   main's CMake registers before it.
3. For every first-party file in that closure, carried the difference between
   the `d457741` and `4e461ea` materializations into the fold owner. Where the
   owner's tokens equalled the old materialization, the owner now holds the new
   one. The pipeline's `DKR_BETA3_SHARED_HEADER` guard copies and absolute
   staged includes were removed; includes are spelled portably.
4. Ported the overlay wiring, the layer fixtures and the service and release
   tooling changes by hand (below).

## Result of the source comparison

`scripts/fold/current-main-closure.json` is re-recorded against `4e461ea`: 921
files, 901 token-identical to what the reference compiled and 20 that differ
on purpose, each listed in the record with its reason:

- Eight carry a fold seam or portability edit onto the v1.0.15 form
  (`party_runtime.cpp`, `vehicle_package.cpp`, `experimental_runtime.cpp`,
  `mod_store.cpp`, `mod_store_install.cpp`, `online_mod_sync.cpp`,
  `f3ddkr_rt64.cpp`, `connection_ui.inl`).
- Seven are deviations from the `d457741` checkpoint whose reference file did
  not change since.
- Five are main PRs #95 and #103 (next section).

This is a token-level source comparison. Per-TU compile settings, preprocessed
tokens, objects and link lines were compared for `d457741` only and have not
been redone.

## Found by building and running it

A full macOS build from both ROMs (prepare, generated payloads, link, launch)
found what the source comparison and the ROM-free CI jobs could not:

- The game target lacked wiring only the release overlay carried: the
  localisation and crash-report libraries, `mod_store/overlay_images.cpp`,
  and the controller-feedback input client and host in place of the
  `sdl3_input_*` sources, which are deleted. Nothing links the full game in CI.
- `symbols/vehicle_symbols.toml` lacked `gCurrentLightIntensity`,
  `gInverseViewMatrixF` and `gViewportLayout`, which v1.0.15's vehicle
  lighting reads. The build compiled and the fields would have been zero.
  The generated header now equals the reference's, token for token. The
  other three symbol headers already did.
- `PeerRelay.cmake`, `SessionChat.cmake` and `OnlineStability.cmake` set
  their source root at file scope. The fold first includes them from inside a
  function, so a second call saw an empty root once `DKRPortGame` exists.
  The root is now set inside each function.
- N64Recomp patch 0003 (from #83) prints a null statement before every
  instruction hook. Regenerated payloads no longer matched the reviewed body
  hashes in `generate_replay_probe.py` and `generate_visual_model_kernel.py`.
  Both now read hooked bodies without it; the hashes are unchanged and match.
  This only shows when payloads are regenerated, so main has it too.
- `library_ui/handoff_ui.inl` queried the rollback runtime unconditionally.
  Builds without it (Apple) now use an inactive view.
- `runtime-recomp/build-inputs.lock.json` is re-recorded from this
  machine's `build/prepared`. All ten inputs changed with v1.0.15's hooks and
  the null statement. A Windows prepare has to reproduce the digests.

Main's v1.0.15 also changed `patches/camera-plus/scene_kernel_pipeline.py`
(road-wheel scope hooks). The release compiles the capsule's pinned kernel,
so that change did not ship, and `scripts/camera_scene_kernel.py` does not
carry it. The fold's regenerated camera kernels equal the capsule's for both
revisions apart from line endings and the null statement.

Result on macOS arm64: the launcher starts and reports 1.0.15, and
`DKR-R --rom <ROM> --timeout 30` runs both revisions to a clean exit (767
display-list tasks on US 1.0, 895 on Rev A). Integrated rollback is off on
Apple, so this does not exercise the online identity.
